# Post-training Research Engineer 지원 준비 다이어리

> 계획을 세우는 데서 끝나지 않고, 실제 학습·실험·지원 준비 기록을 다음 계획으로 이어가는 공개 실행 다이어리입니다.

## 서비스 소개

AI Research Engineer, 특히 post-training 분야를 준비하는 과정에서는 공부한 내용, 실험 결과, 포트폴리오 작업, 코딩 테스트 준비가 여러 도구와 메모로 흩어지기 쉽습니다. 계획은 세웠지만 실제로 얼마나 진행했는지, 예상과 실제에 어떤 차이가 있었는지, 다음에 무엇을 바꿔야 하는지는 따로 남지 않는 경우가 많습니다.

이 서비스는 그 단절을 줄이기 위해 **Plan–Do–See** 흐름을 하나의 기록으로 연결합니다.

- **Plan**: 이번 기간에 달성할 목표와 성공 기준을 구체적으로 정합니다.
- **Do**: 계획에 속한 할 일을 실제로 수행하고 시작·종료 시각과 실행 중 문제를 기록합니다.
- **See**: 계획과 실제의 차이를 수치와 원본 기록으로 확인하고, 개선점을 다음 계획으로 연결합니다.

## 누구를 위한 서비스인가요?

- Post-training·fine-tuning·RLHF·RLVR·데이터 합성 등을 공부하는 사람
- AI/ML 연구 엔지니어 취업을 준비하며 학습과 포트폴리오를 함께 관리하려는 사람
- 단순한 할 일 목록보다 **예상 시간, 실제 시간, 결과, 다음 액션**을 남기고 싶은 사람

기획 배경은 [Upstage AI Research Engineer - Post-training 공고](https://careers.upstage.ai/ko/o/194876)를 참고했습니다. 다만 이 서비스는 특정 회사에 지원했다는 사실을 기록하는 도구가 아니라, 목표 직무를 준비하는 과정을 구조화하는 도구입니다.

## 핵심 경험

### 계획을 실행 가능한 단위로 쪼갭니다

계획에는 기간, 우선순위, 성공 기준, 예상 소요 시간을 함께 기록합니다. 계획을 수정할 때는 기존 내용을 이력으로 보존해 처음의 판단과 현재의 판단을 비교할 수 있습니다.

### 할 일이 실제 기록으로 남습니다

할 일은 마감일, 우선순위, 태그, 예상 시간을 기준으로 검색·필터·정렬할 수 있습니다. 완료 여부만 표시하는 대신 실제 시작 시각, 종료 시각, 소요 시간, 실행 중 문제를 기록합니다.

### 숫자에서 원본 기록으로 이동합니다

대시보드의 계획 수, 완료 수, 지연 수, 차단 수, 예상 시간과 실제 시간의 차이는 집계 숫자로 끝나지 않습니다. 각 숫자에서 해당 원본 계획·할 일·실행 기록을 확인할 수 있도록 설계했습니다.

### 회고가 다음 계획으로 이어집니다

회고에서 정한 개선점을 다음 계획과 연결합니다. 회고가 별도의 감상문으로 끝나지 않고, 다음 실행의 입력값이 되도록 만든 구조입니다.

### 새로고침해도 기록이 사라지지 않습니다

화면 상태가 아니라 서버 데이터베이스를 기준으로 동작합니다. 계획, 할 일, 실행 기록, 회고, 수정 이력은 API를 통해 저장되고 다시 불러옵니다.

## 데이터 신뢰성을 위한 설계

이 서비스는 화면의 편의 기능만으로 기록을 신뢰하지 않습니다.

- 계획 수정 전 현재 상태를 revision으로 보존합니다.
- 할 일 삭제는 soft delete로 처리해 과거 기록의 참조를 유지합니다.
- 실제 소요 시간은 사용자가 임의로 입력하는 값이 아니라 시작·종료 시각으로 계산합니다.
- 완료 요청에는 idempotency key와 데이터베이스 제약을 적용해 중복 기록을 막습니다.
- 같은 정렬 값에서도 결과가 흔들리지 않도록 보조 정렬 기준을 사용합니다.
- 사용자가 입력한 HTML·스크립트 형태의 텍스트는 실행하지 않고 문자로 표시합니다.
- 브라우저에 데이터베이스 자격 증명을 전달하지 않고 서버 API를 통해서만 저장합니다.

## 서비스 범위

현재 서비스는 ALEPH Studio T06의 요구 범위에 맞춰 하나의 공개 작업공간으로 동작합니다.

- 로그인·회원가입·OAuth 없음
- 공개 결과 URL을 아는 사람은 기록을 볼 수 있음
- 회사 지원 자동 제출이나 AI 자동 첨삭 기능은 포함하지 않음
- 실제 개인정보, 연락처, 비밀번호, API 키, 비공개 지원서 원문을 저장하지 않음

따라서 공개 화면에는 개인 식별 정보나 비밀 정보를 입력하지 않는 것을 전제로 합니다.

## 기술 구조

| 영역 | 사용 기술 |
| --- | --- |
| 화면·서버 | Next.js App Router, React, TypeScript |
| API | Next.js Route Handlers |
| 데이터베이스 | Supabase PostgreSQL |
| 입력 검증 | Zod |
| 테스트 | Vitest, React Testing Library, Playwright |
| 배포 대상 | GitHub 연동 Vercel |
| 시간대 기준 | Asia/Seoul |

브라우저는 화면을 제공받고 서버 API와 통신합니다. 서버 API가 입력을 검증하고 도메인 규칙을 적용한 뒤 Supabase PostgreSQL에 기록하는 구조입니다.

## 저장소 구조

```text
app/                 Next.js 화면과 API Route Handler
components/          대시보드·계획·할 일·실행·회고 UI
lib/domain/          도메인 타입·검증·집계·export 규칙
lib/server/          Supabase 접근·Repository·Service
supabase/migrations/ 데이터베이스 스키마와 트랜잭션 함수
contracts/           공개 export 데이터 계약
tests/               단위·컴포넌트·API·E2E 테스트
```

## 현재 구현된 기록 흐름

1. 공개 작업공간에서 계획을 작성합니다.
2. 계획에 속한 할 일을 만들고 우선순위·태그·예상 시간을 정합니다.
3. 실제 수행 시 실행 기록을 남깁니다.
4. 완료·재진행·삭제와 같은 상태 변화를 기록합니다.
5. 대시보드에서 예상과 실제의 차이를 확인합니다.
6. 회고의 개선점을 다음 계획으로 연결합니다.
7. 전체 공개 작업공간 자료를 JSON으로 export합니다.

## 프로젝트 진행 방향

현재 GitHub 저장소에는 서비스의 화면, 서버 API, 도메인 로직, 데이터베이스 마이그레이션, 테스트 코드가 포함되어 있습니다. 다음 단계는 Supabase PostgreSQL에 실제 스키마와 초기 공개 작업공간을 적용하고, 환경변수를 설정한 뒤 Vercel에 공개 HTTPS 서비스로 배포하는 것입니다.
