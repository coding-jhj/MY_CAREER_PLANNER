# Post-training Research Engineer 지원 준비 다이어리 설계

## 1. 문서 상태

- 상태: 설계 초안
- 작성일: 2026-09-07
- 대상 과제: ALEPH Studio T06 — 플랜투씨 다이어리 1
- 공개 화면 제목: `Post-training Research Engineer 지원 준비`
- 공개 화면에 표시하지 않는 정보: 회사명, 연락처, 비밀번호, API 키, 개인 식별 정보

이 문서는 T06 구현을 시작하기 전에 제품 목표, 데이터 구조, 핵심 규칙, 검증 방법을 고정하기 위한 설계 문서다. 구현은 이 문서의 승인 이후 시작한다.

## 2. 근거와 목표

### 2.1 과제 근거

T06은 계획(Plan), 실제 실행(Do), 돌아보기(See)가 하나의 서버 데이터 흐름으로 이어지는 앱을 요구한다. 로그인은 구현하지 않으며, 공개 결과 URL을 새로고침해도 계획·할 일·실행 기록·회고가 유지되어야 한다.

필수 결과물은 다음과 같다.

- 공개 결과 URL
- 전체 소스 상태를 가리키는 full commit URL
- 3단계 이내의 재현·통과 확인 4단계
- AI에게 맡긴 일, 직접 판단한 일, AI 제안을 따르지 않은 일을 적은 3줄
- 계획·할 일·실행 기록·회고가 실제 데이터베이스에 저장된 결과

### 2.2 목표 직무 근거

기획의 실제 데이터는 사용자가 목표로 정한 Post-training Research Engineer 지원 준비에 맞춘다. 참고한 공식 공고는 다음과 같다.

- 공식 공고: [AI Research Engineer - Post-training](https://careers.upstage.ai/ko/o/194876)
- 공고에서 제시한 관심 영역: General Agent, Science Agent, Coding Agent, Office Work Agent, Computer Use Agent
- 공고에서 제시한 기술 방향: LLM/VLM post-training·fine-tuning, RLHF·RLVR·OPD, 고품질 데이터 필터링, Agent Harness, 데이터 합성, 성능 최적화
- 공고에서 제시한 준비 항목: post-training/fine-tuning 경험, Foundation Model 트렌드 이해, ML·NLP 연구·출판 경험, 알고리즘·딥러닝 코딩 테스트, 기술 인터뷰

이 공고의 요건을 이미 충족했다고 표시하지 않는다. 실제 보유 경험은 완료·진행 중·보완 필요 상태로 정직하게 기록한다.

### 2.3 제품 목표

이 앱은 채용 사이트나 일반적인 할 일 목록이 아니다. 목표 직무 준비를 다음 기록으로 연결하는 공개형 실행 다이어리다.

> 준비 계획을 세우고 → 실제 학습·실험·지원 준비를 기록하고 → 예상과 실제의 차이를 확인하고 → 다음 계획을 수정한다.

## 3. 범위

### 3.1 포함 범위

1. 계획 생성·수정·수정 이력 확인
2. 계획에 속한 할 일 생성·수정·완료·되돌리기·삭제
3. 마감일·우선순위·태그·예상 시간 관리
4. 검색·조건 필터·결정적 정렬
5. 실제 실행 기록의 시작·종료·소요 시간·문제 기록
6. 완료 중복 요청 방지
7. 계획 대비 실제 결과 집계
8. 집계 숫자에서 원본 기록으로 이동
9. 회고의 개선점을 다음 계획으로 연결
10. 전체 자료 JSON export
11. 새로고침 후 서버 데이터 복원
12. 스크립트 형태 입력을 실행하지 않고 문자로 표시

### 3.2 제외 범위

- 회원가입·로그인·OAuth·CAPTCHA
- 회사 채용 지원 자동 제출
- 실제 지원서 원문·이메일·전화번호 저장
- AI API를 이용한 자동 첨삭·추천·생성
- 여러 사용자의 계정·권한 관리
- T06에서 요구하지 않는 실시간 알림·캘린더·소셜 기능

T06은 로그인과 잠금 기능을 요구하지 않으므로 단일 공개 작업공간으로 구현한다. 공개 URL을 아는 사람이 내용을 볼 수 있다는 안내를 첫 화면에 표시한다.

## 4. 기술 구조

### 4.1 확정 구조

- 애플리케이션: Next.js
- 서버 API: Next.js App Router Route Handler (`app/api`)
- 데이터베이스: Supabase PostgreSQL
- 저장소: 단일 GitHub 저장소
- 배포: 공개 HTTPS URL
- 시간대: `Asia/Seoul`

브라우저는 데이터베이스에 직접 쓰지 않는다. 모든 생성·수정·완료·집계·export는 서버 API를 거친다.

```text
공개 브라우저
    ↓ HTTPS
Next.js 화면 + 서버 API
    ↓ 서버 측 DB 접근
Supabase PostgreSQL
```

### 4.2 단일 공개 작업공간

T06에서는 사용자 인증을 만들지 않는다. 모든 데이터는 하나의 공개 작업공간에 속한다. `workspace_id`를 각 주요 테이블에 저장해 이후 잠금·계정 기능을 추가할 수 있는 경계를 남기되, T06 화면에는 로그인 절차를 노출하지 않는다.

## 5. 데이터 모델

### 5.1 `workspaces`

| 필드 | 타입 | 규칙 |
|---|---|---|
| `id` | UUID | 기본 키 |
| `slug` | text | `public` 고정 |
| `title` | text | 공개 화면 제목 |
| `timezone` | text | `Asia/Seoul` |
| `created_at` | timestamptz | 서버 생성 |

초기 배포 시 `public` 작업공간 하나만 생성한다.

### 5.2 `plans`

| 필드 | 타입 | 규칙 |
|---|---|---|
| `id` | UUID | 계획 ID, 수정해도 유지 |
| `workspace_id` | UUID | `workspaces.id` 참조 |
| `title` | text | 필수 |
| `start_date` | date | 필수 |
| `end_date` | date | 필수, 시작일 이상 |
| `priority` | integer | 1~5 |
| `success_criteria` | text | 필수 |
| `estimated_minutes` | integer | 0 이상 |
| `created_at` | timestamptz | 서버 생성 |
| `updated_at` | timestamptz | 서버 갱신 |
| `archived_at` | timestamptz nullable | 보관 시 사용 |

### 5.3 `plan_revisions`

계획을 수정하기 전에 현재 값을 스냅샷으로 저장한다.

| 필드 | 타입 | 규칙 |
|---|---|---|
| `id` | UUID | 기본 키 |
| `plan_id` | UUID | `plans.id` 참조 |
| `revision_no` | integer | 계획별 순번 |
| `title` | text | 수정 전 제목 |
| `start_date` | date | 수정 전 시작일 |
| `end_date` | date | 수정 전 종료일 |
| `priority` | integer | 수정 전 우선순위 |
| `success_criteria` | text | 수정 전 성공 기준 |
| `estimated_minutes` | integer | 수정 전 예상 시간 |
| `saved_at` | timestamptz | 서버 생성 |

계획 수정은 `plan_revisions` 삽입과 `plans` 갱신을 하나의 트랜잭션으로 처리한다.

### 5.4 `tasks`

| 필드 | 타입 | 규칙 |
|---|---|---|
| `id` | UUID | 기본 키 |
| `plan_id` | UUID | 계획 참조 |
| `title` | text | 필수 |
| `due_date` | date nullable | 마감일 |
| `priority` | integer | 1~5 |
| `tag` | text | 예: `post-training`, `experiment`, `coding-test` |
| `estimated_minutes` | integer | 0 이상 |
| `status` | text | `todo`, `in_progress`, `done` |
| `blocked_reason` | text nullable | 입력되면 막힌 할 일로 집계 |
| `completed_at` | timestamptz nullable | 완료 시각 |
| `deleted_at` | timestamptz nullable | 삭제는 soft delete |
| `created_at` | timestamptz | 서버 생성 |
| `updated_at` | timestamptz | 서버 갱신 |

실제 삭제 대신 `deleted_at`을 사용한다. 그래야 실행 기록과 계획 수정 이력의 참조가 끊기지 않는다. 집계에서는 `deleted_at IS NULL`인 할 일만 포함한다.

### 5.5 `execution_records`

| 필드 | 타입 | 규칙 |
|---|---|---|
| `id` | UUID | 기본 키 |
| `task_id` | UUID | 할 일 참조 |
| `started_at` | timestamptz | 필수 |
| `ended_at` | timestamptz | 필수, 시작 이후 |
| `actual_minutes` | integer | 서버가 시작·종료 차이로 계산해 저장 |
| `missed_reason` | text nullable | 실행 중 문제·미실행 사유 |
| `idempotency_key` | UUID | 완료 요청 중복 방지 |
| `created_at` | timestamptz | 서버 생성 |

`idempotency_key`에는 unique 제약을 건다. 같은 완료 요청이 다시 도착하면 기존 결과를 반환하고 새 실행 기록을 만들지 않는다.

### 5.6 `reviews`

집계 수치는 현재 데이터에서 계산하고, 회고 테이블에는 사람이 정한 개선점만 저장한다.

| 필드 | 타입 | 규칙 |
|---|---|---|
| `id` | UUID | 기본 키 |
| `plan_id` | UUID | 회고 대상 계획 |
| `correction_text` | text | 다음 계획으로 넘길 개선점 |
| `next_plan_id` | UUID nullable | 연결된 다음 계획 |
| `created_at` | timestamptz | 서버 생성 |

## 6. 핵심 업무 규칙

### 6.1 계획 수정 이력

1. 현재 계획을 `plan_revisions`에 저장한다.
2. 같은 `plans.id`의 현재 값을 갱신한다.
3. 화면에서는 현재 계획과 수정 이력을 모두 볼 수 있어야 한다.

### 6.2 할 일 정렬

정렬 기준을 화면에 표시한다. 같은 값이 있을 때 결과가 매번 달라지지 않도록 다음 보조 정렬을 사용한다.

- 우선순위: `priority ASC`, `due_date ASC`, `id ASC`
- 마감일: `due_date ASC NULLS LAST`, `priority ASC`, `id ASC`
- 예상 시간: `estimated_minutes ASC`, `due_date ASC`, `id ASC`
- 생성순: `created_at ASC`, `id ASC`

검색·필터·정렬은 서버 쿼리 기준으로 처리하고, 현재 적용된 기준을 화면에 표시한다.

### 6.3 완료 중복 방지

완료 버튼을 연속으로 눌러도 다음 세 겹으로 보호한다.

1. 화면에서 요청 중 버튼을 잠근다.
2. 서버 API가 idempotency key를 검증한다.
3. 데이터베이스 unique 제약과 트랜잭션으로 중복 삽입을 차단한다.

버튼 잠금은 사용자 경험을 위한 보조 수단일 뿐, 데이터 정합성의 유일한 방어 수단으로 사용하지 않는다.

### 6.4 집계

- 계획 수: 삭제되지 않은 할 일 수
- 완료 수: 삭제되지 않았고 `status = done`인 할 일 수
- 지연 수: 삭제되지 않았고 `status != done`이며 서울 날짜 기준 마감일이 오늘보다 이전인 할 일 수
- 막힘 수: 삭제되지 않았고 `trim(blocked_reason) != ''`인 할 일 수
- 예상 시간: 대상 할 일의 `estimated_minutes` 합계
- 실제 시간: 대상 할 일에 연결된 `execution_records.actual_minutes` 합계
- 차이: 실제 시간 - 예상 시간
- 데이터가 없을 때 시간 집계값: 0

각 집계 응답에는 숫자뿐 아니라 해당 숫자를 만든 `task_id` 목록도 포함한다. 클릭하면 같은 필터가 적용된 상세 목록으로 이동한다.

### 6.5 회고에서 다음 계획으로 연결

회고 화면에서 개선점 한 건을 입력하고 `다음 계획으로 넘기기`를 누르면 새 `plans` 레코드를 만들거나 기존 다음 계획에 연결한다. 생성된 계획에는 원본 `review.id`를 기록해 연결 관계를 추적한다.

## 7. 화면 설계

### 7.1 첫 화면 `/`

- 공개 안내 문구
- 현재 계획 제목·기간·우선순위·성공 기준
- Plan / Do / See 진행 표시
- 계획·완료·지연·막힘 집계
- 예상 시간·실제 시간·차이
- `계획 수정`, `할 일 관리`, `돌아보기`, `JSON 내보내기` 버튼

### 7.2 계획 패널

- 계획 생성
- 계획 수정
- 현재 계획과 수정 이력 비교
- 수정 전 값이 남아 있는지 확인

### 7.3 할 일 패널

- 할 일 생성·수정·삭제
- 완료·진행 중 되돌리기
- 마감일·우선순위·태그·예상 시간 입력
- 검색어
- 상태·태그·우선순위 필터
- 정렬 기준 선택
- 현재 정렬 기준 표시

### 7.4 실행 기록 패널

- 실행할 할 일 선택
- 시작 시각·종료 시각 입력
- 서버 계산 실제 소요 시간 표시
- 문제·미실행 이유 입력
- 완료 기록 저장
- 같은 요청 재전송 시 기존 기록 재사용

### 7.5 돌아보기 패널

- 계획 수·완료 수·지연 수·막힘 수
- 예상 시간·실제 시간·차이
- 각 숫자를 클릭하면 원본 할 일 목록으로 이동
- 개선점 입력
- 다음 계획으로 넘기기

### 7.6 export

다음 내용을 하나의 JSON 파일로 내려받는다.

- workspace
- 현재 plans
- plan_revisions
- tasks
- execution_records
- reviews
- export 생성 시각
- 스키마 버전

최종 저장소에는 `contracts/pds-schema-v2.json`을 포함한다.

## 8. 공개 데이터와 안전성

- 첫 화면에 로그인 없음·공개 접근 안내를 표시한다.
- 실제 지원서 원문, 이메일, 전화번호, 주소, 비밀번호, API 키를 입력 데이터에 넣지 않는다.
- 모든 사용자 입력은 텍스트로 렌더링한다.
- HTML을 직접 삽입하지 않는다.
- `<script>alert(1)</script>` 입력이 실행되지 않고 문자 그대로 보이는지 검증한다.
- export에도 비밀값이 포함되지 않도록 허용 필드만 직렬화한다.

## 9. 초기 공개 데이터

배포 직후 결과 URL에서 바로 검증할 수 있도록 사용자의 실제 준비 계획과 실제 실행 기록을 넣는다. 허구의 완료 기록이나 임의의 소요 시간을 실제 경험처럼 표시하지 않는다. 아래 항목은 초기 데이터의 내용과 구조를 정하는 기준이며, 실행 시간과 회고 문장은 사용자가 실제로 수행한 뒤 입력한다.

6. GitHub·포트폴리오 결과 정리
7. 알고리즘·딥러닝 코딩 테스트 준비

사용자가 실제로 수행한 활동 중 완료·진행 중·지연·막힘 상태가 드러나는 항목을 입력한다. 실행 기록은 실제 수행한 기록으로 최소 3건을 저장한다. 실제 기록이 없는 항목은 완료로 표시하지 않는다.

## 10. 서버 API 경계

화면은 아래 API만 사용한다. 데이터베이스 접근은 서버 코드에만 둔다.

| 메서드 | 경로 | 역할 |
|---|---|---|
| `GET` | `/api/dashboard` | 현재 계획·집계·최근 기록 조회 |
| `POST` | `/api/plans` | 계획 생성 |
| `PATCH` | `/api/plans/:id` | 계획 수정 전 이력 저장 후 갱신 |
| `GET` | `/api/plans/:id/revisions` | 계획 수정 이력 조회 |
| `POST` | `/api/tasks` | 할 일 생성 |
| `PATCH` | `/api/tasks/:id` | 할 일 수정·상태 변경 |
| `DELETE` | `/api/tasks/:id` | soft delete |
| `GET` | `/api/tasks` | 검색·필터·정렬된 할 일 조회 |
| `POST` | `/api/tasks/:id/executions` | 실행 기록 저장 |
| `POST` | `/api/tasks/:id/complete` | idempotency key로 완료 처리 |
| `POST` | `/api/tasks/:id/reopen` | 완료 할 일을 진행 중으로 되돌리기 |
| `GET` | `/api/reviews/:planId` | 집계와 원본 ID 목록 조회 |
| `POST` | `/api/reviews/:planId/corrections` | 회고 개선점과 다음 계획 연결 |
| `GET` | `/api/export` | 허용 필드만 JSON으로 export |

## 11. 오류 처리와 검증 규칙

- 필수 필드 누락·잘못된 날짜·음수 시간·허용하지 않은 상태는 `400`과 필드별 오류로 반환한다.
- 존재하지 않거나 삭제된 ID는 `404`로 반환한다.
- 시작 시각이 종료 시각보다 늦으면 실행 기록을 저장하지 않는다.
- 같은 `idempotency_key`가 다시 오면 새 행을 만들지 않고 기존 실행 기록을 반환한다.
- 데이터베이스 트랜잭션이 실패하면 계획·이력·실행 기록 중 일부만 저장된 상태를 만들지 않는다.
- export 실패 시 다운로드 성공처럼 보이는 빈 파일을 만들지 않고 화면에 실패 원인을 표시한다.
- 저장 실패 후에도 입력 폼의 값은 유지해 사용자가 다시 제출할 수 있게 한다.
- 서버 오류 응답에는 비밀번호·데이터베이스 연결 문자열·환경 변수 값을 포함하지 않는다.

## 12. 테스트 설계

### API·데이터 테스트

- 계획 생성 시 기간·우선순위·성공 기준·예상 시간이 저장되는지 확인한다.
- 계획 수정 시 기존 값이 `plan_revisions`에 저장되고 현재 계획 ID가 유지되는지 확인한다.
- 같은 완료 요청을 두 번 보내도 `execution_records`가 한 건만 생성되는지 확인한다.
- 완료→되돌리기→완료 상태 전환이 가능하고 완료 집계가 현재 상태를 반영하는지 확인한다.
- soft delete한 할 일이 집계에서 제외되는지 확인한다.
- 예상 시간·실제 시간·차이가 같은 분 단위로 계산되는지 확인한다.
- export JSON에 workspace를 포함한 여섯 개 자료 집합과 스키마 버전이 포함되는지 확인한다.

### 브라우저 수동 테스트

화면에서는 이 문서의 T06 시나리오 A~E를 순서대로 수행하고, 각 시나리오의 통과 증거 화면을 남긴다.

## 13. T06 검증 시나리오

### 시나리오 A — 계획

1. 첫 화면에서 계획 수정 화면으로 이동한다.
2. 기간·우선순위·성공 기준·예상 시간을 수정한다.
3. 저장 후 현재 값과 수정 전 이력을 확인한다.

통과 조건: 계획 ID는 유지되고 수정 전 값이 별도 이력으로 남는다.

### 시나리오 B — 할 일

1. 할 일을 5개 이상 만든다.
2. 하나를 수정·완료·되돌리기·삭제한다.
3. 검색·필터·정렬을 각각 실행한다.

통과 조건: 모든 조작이 저장되고 정렬 기준과 결과가 일치한다.

### 시나리오 C — 실제 실행

1. 할 일에 시작·종료 시각과 문제 기록을 입력한다.
2. 완료 버튼을 빠르게 두 번 누른다.
3. 실행 기록과 완료 집계를 확인한다.

통과 조건: 실행 기록은 한 건만 생성되고 완료 수는 한 번만 증가한다.

### 시나리오 D — 돌아보기

1. 계획·완료·지연·막힘 숫자를 확인한다.
2. 숫자를 클릭해 원본 할 일 목록으로 이동한다.
3. 예상 시간과 실제 시간의 차이를 확인한다.
4. 개선점 하나를 다음 계획으로 넘긴다.

통과 조건: 숫자와 원본 목록이 일치하고 개선점이 다음 계획에 남는다.

### 시나리오 E — 지속성·안전성

1. 계획·할 일·실행 기록을 저장한다.
2. 새로고침한다.
3. ID·값·단위가 같은지 확인한다.
4. 스크립트 형태 문자를 입력하고 실행되지 않는지 확인한다.
5. JSON export를 내려받아 전체 자료가 한 파일에 있는지 확인한다.

## 14. 제출 전 확인

- 공개 결과 URL이 시크릿 창에서 열린다.
- 로그인·계정 생성·OAuth·CAPTCHA가 필요하지 않다.
- 소스 URL이 저장소 첫 화면이 아니라 full commit URL이다.
- `contracts/pds-schema-v2.json`이 최종 커밋에 포함된다.
- README 또는 제출란에 재현·통과 확인 4단계가 있다.
- AI에게 맡긴 일·직접 판단한 일·따르지 않은 제안이 각각 한 줄씩 있다.
- 실제 개인 데이터와 비밀값이 공개 데이터에 없다.

## 15. 설계 완료 조건

다음 항목이 구현되고 검증되면 T06 설계의 완료로 본다.

1. Plan·Do·See가 서버 DB의 관계로 연결된다.
2. 계획 수정 이력이 보존된다.
3. 할 일 CRUD·검색·필터·정렬이 동작한다.
4. 실행 기록이 계획 값을 덮어쓰지 않는다.
5. 완료 중복 요청이 데이터베이스 수준에서 제거된다.
6. 돌아보기 집계가 원본 기록과 일치한다.
7. 회고 개선점이 다음 계획으로 이어진다.
8. 새로고침·export·스크립트 문자 검증이 통과한다.
9. 공개 URL과 full commit URL로 재현할 수 있다.
